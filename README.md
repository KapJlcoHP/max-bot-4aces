# МедМаршрут — бот + мини-приложение для платформы MAX

Хакатон MAX, команда **4Aces**, кейс «Забота о людях».

**Назначение.** МедМаршрут — цифровой помощник пациента с длительным лечением.
Врач назначил — пациент за 30 секунд зафиксировал назначения в маршруте; дальше
продукт сам ведёт по маршруту: напоминает о шагах, визитах, измерениях и приёме
лекарств, собирает дневники здоровья и формирует «Сводку для врача» в PDF
(только факты за 30 дней — без диагнозов и оценок «норма/не норма»).

## Основной пользовательский сценарий

1. В мессенджере MAX найдите бота по нику **@t24_hakaton_max_bot** (поиск по
   имени пользователя) и нажмите «Начать» / отправьте `/start` →
   кнопка «Открыть МедМаршрут» запускает мини-приложение (вход по подписанному
   `initData` из MAX, без регистрации).
2. Онбординг: город из списка пилотных регионов, согласие на обработку данных (152-ФЗ) —
   блокирующий шаг.
3. Маршрут: один из **8 доступных шаблонов** (32 базовых шага суммарно) или свой
   маршрут в конструкторе. Семейная заготовка скрыта, общие права/уведомления не подключены.
4. У шагов явный смысл: запись, врачебный визит, исследование, задача/документ,
   конечный этап процесса. Назначения после реальной консультации вносятся вручную;
   шаблон не назначает всем заранее анализы/лечение/повторные визиты.
5. Ведение: отметка шагов, курсы лекарств с отметкой приёма, дневники здоровья
   (давление, вес, сахар, самочувствие со шкалой боли).
6. Бот напоминает только о текущем шаге: по дате накануне/в день, за час — только
   при точном времени. О приёмах лекарств и
   дневниках — по расписанию пользователя; `/svodka` присылает сводку PDF в чат.
7. На приёме пациент показывает «Сводку для врача» (PDF или экран).

## Состав и архитектура

```
zabota/
├── core/          # ядро: config, модели SQLAlchemy, сид справочников, демо-данные, pydantic-схемы
│   └── db/        # seed (справочники из content/*.json), demo (команда /demo)
├── bot/           # чат-бот (maxapi, long polling): команды, напоминания (scheduler), PDF в чат
├── server/        # FastAPI: REST /api/v1 (+ раздаёт собранный мини-ап и /docs)
├── web/           # мини-приложение: React 19 + TypeScript + MAX UI (@maxhub/max-ui)
├── content/       # контент вне кода: catalog.json, scenarios.json, regions.json, шрифты PDF
├── deploy/        # Caddyfile для prod-профиля
├── tests/         # автотесты (pytest): авторизация, маршрут, планировщик, тест-токен
├── DATA-API.yaml  # конфигурация обязательных проверок API (формат кейса)
├── TEST-DATA.json # тестовые данные и порядок проверки API
├── openapi.json   # OpenAPI 3.1 (генерируется scripts/export_openapi.py)
├── Dockerfile, compose.yaml, requirements.txt, .env.example
```

- **API:** FastAPI + SQLAlchemy 2.0 + SQLite, pydantic v2 (см. `requirements.txt`)
- **Бот:** [maxapi](https://love-apples.github.io/maxapi/) (long polling), анти-фlood, рестарт-цикл с backoff
- **Мини-ап:** Vite + React 19, MAX Bridge (`window.WebApp`), MAX UI; прод-сборка `web/dist` раздаётся API
- **Аутентификация:** подписанный `initData` (HMAC-SHA256) в заголовке `X-Max-Init-Data`,
  срок жизни 24 ч; для машинной проверки API — заголовок `X-Test-Token` (см. ниже)

## Запуск одной командой (Docker)

```bash
docker compose up -d --build
```

→ API и мини-приложение: **http://localhost:8000** (OpenAPI: http://localhost:8000/openapi.json, `/docs`).

Чат-бот (нужен `MAX_BOT_TOKEN` в `.env`; **экземпляр должен быть ровно один** — long polling):

```bash
docker compose --profile bot up -d --build
```

Прод с HTTPS (VPS + домен, см. `MEDROUTE_DOMAIN`):

```bash
docker compose --profile prod --profile bot up -d --build
```

### Локальная установка и проверки без Docker

Для Linux/macOS нужен Python 3.12 и Node.js 24. Версии зафиксированы в
`.python-version` и `.nvmrc`. Установка выполняется только внутри проекта:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-smoke.txt
npm --prefix web ci --no-audit --no-fund
```

Единая команда тестов, не требующая сети после установки зависимостей:

```bash
make test
```

Полная локальная проверка с typecheck и production-сборкой:

```bash
make check
```

Без Docker API запускается командой `.venv/bin/python -m uvicorn
server.main:app --reload --host 127.0.0.1 --port 8000`, а Vite — из `web/`
командой `npm run dev`. Бот запускается отдельно командой `.venv/bin/python
run_bot.py`; для long polling должен работать ровно один экземпляр.
Windows-обёртки `run_api.bat` и `run.bat` выполняют соответствующие API- и
bot-команды.

## Расписание шагов

- Новые маршруты из обычных шаблонов создаются без назначенных дат и времени.
  Пользователь задаёт расписание сам; существующие сроки при обновлении сохраняются.
  Только `/demo` явно заполняет синтетическое расписание относительно даты пользователя.
- Дата и время события трактуются в часовом поясе профиля. Время необязательно,
  но не может быть задано без даты; API нормализует его в `HH:MM`.
- `PATCH /api/v1/route/steps/{id}` различает пропущенное поле и `null`:
  `{}` ничего не меняет; `{"deadline_time":"14:30"}` сохраняет дату;
  `{"deadline_time":null}` убирает только время;
  `{"deadline":null}` убирает дату и зависимое время.
  Одновременные `deadline:null` и непустое `deadline_time` отклоняются.
  Обычный перенос даты сохраняет имеющееся время. Выполненный шаг не редактируется.
- Стандартные уведомления маршрута получает только `current`, не `pending`/`done`.
  Без даты уведомлений нет. Для даты без времени варианты «накануне» и «в день»
  используют `step_day_before_time` из профиля; часового пуша нет, время приёма
  не выдумывается. Для точного времени работают «накануне», «за час», «в момент».
  Каждый вариант и глобальный переключатель уведомлений можно отключить.
- В карточке шагов доступны взаимоисключающие режимы `reminder_mode`:
  `profile` («Как в профиле»), `day` («За день»), `hour` («За час», при точном
  времени события), `custom` («В другое время…», одно отдельное уведомление).
  Явный режим заменяет стандартные варианты этого шага, но глобальное отключение
  уведомлений действует на все режимы. По умолчанию используется `profile`.
- `reminder_at` — отдельный абсолютный момент уведомления, не время события.
  Ввод без смещения трактуется в поясе профиля; API возвращает UTC со смещением.
  Прошлое время, разрыв/неоднозначность при переводе часов отклоняются; API может
  принять однозначный момент с явным смещением. Повтор уже сохранённой настройки —
  no-op даже после её наступления, он не создаёт нового уведомления.
- Перенос события с `custom` требует заново проверить и подтвердить отдельное
  напоминание либо сбросить его. В API для подтверждения явно передаются оба поля
  `reminder_mode` и `reminder_at`. Очистка даты удаляет зависимое время и переопределение.
- Только текущий шаг может отправлять уведомления. При активации не догоняются
  уже прошедшие окна, включая собственный момент будущего шага. Для уже текущего
  шага сетевые повторы собственного уведомления допускаются в течение 24 часов
  после его момента; после успешной отправки оно не повторяется.
- Изменение расписания/режима получает новую ревизию дедупа. Старый отложенный
  receipt не подавляет новое расписание. Перед отправкой шаг повторно проверяется
  по свежему состоянию БД; завершение/удаление/перенос/выключение уведомлений
  исключают устаревший push. Изменение во время самого внешнего сетевого вызова
  отменить гарантированно нельзя — это не exactly-once протокол MAX.
- Поля даты/времени есть у своего шага, назначений и редактора карточки. Памятка
  «У некоторых шагов не указана дата» ведёт к первому незавершённому шагу без даты
  и не требует выдумывать неизвестный срок. Это подсказка по правилам, без AI.

## Завершение шага и назначения врача

- Только у `kind=visit` «Я это сделал» открывает форму, но ещё не завершает визит.
  Закрытие или «Отмена» не меняют маршрут. «Без назначений» явно завершает шаг;
  подтверждение пакета завершает его и добавляет все назначения одной транзакцией.
  Обычные шаги завершаются без этой формы. `source=doctor` или слово «приём» в названии
  не определяют вид. Блок «Почему этот шаг появился» удалён, источник сохранён.
- `POST /api/v1/route/steps/{id}/assignments` принимает UUID `request_id`,
  булево `complete` и массив `assignments` с `title`, `kind`, необязательными `deadline`,
  `deadline_time` и `place` (для записи — отдельная `appointment_date`). `complete:true`
  требует текущего врачебного визита и допускает
  пустой массив; `complete:false` добавляет непустой пакет после уже выполненного
  врачебного визита, не изменяя историческую отметку выполнения. Источник новых шагов — `doctor`.
  «Анализы», «УЗИ», «Прививка», разовая процедура — `investigation`; «Приём специалиста» —
  `visit`; этап курса — `process`. Свободный ввод имеет явный выбор вида.
- Пакет вставляется сразу после исходного шага в порядке массива. Позиции
  последовательны; первый незавершённый шаг — единственный `current`, остальные
  незавершённые — `pending`. Одинаковые названия разрешены: ответ содержит
  `added_step_ids`, `step`, `route`, `next_step`, поиск нового шага по названию не нужен.
- Повтор того же UUID и нормализованного содержимого возвращает исходный результат
  без повторного изменения маршрута. Изменение содержимого или исходного шага при
  том же UUID — 409. UUID ограничен пользователем; receipt сохраняется даже после
  удаления/замены маршрута и удаляется вместе с аккаунтом. Снимок ответа при повторе
  исторический: актуальное состояние нужно читать через `GET /api/v1/route`.
- При неопределённом сетевом исходе форма сохраняет исходную отправку и разрешает
  только её безопасный повтор с тем же UUID, а не создание нового пакета. Это
  состояние хранится только в открытой карточке: после её закрытия/перезагрузки
  сначала проверьте маршрут, прежде чем добавлять назначения повторно.
  Отклонённый запрос с ошибкой валидации позволяет исправить черновик;
  конфликт состояния предлагает обновить маршрут. Успех показывается после ответа.
- Полностью выполненный маршрут сохраняет таймлайн: можно открыть выполненный шаг,
  отменить выполнение, добавить назначения к визиту или новый шаг и продолжить маршрут.
- При запуске `init_db` создаёт новую таблицу `route_assignment_receipts` без
  изменения существующих сроков. Она содержит снимки результатов операций;
  резервное копирование и удаление пользовательских данных должны учитывать её.
  Изменение рабочей БД/деплой требуют отдельного согласования.

## Запись на конкретное событие (S6–S9)

Точный контракт: [ROUTE-SEMANTICS.md](ROUTE-SEMANTICS.md), машинная схема — `openapi.json`.

- `kind`: `unknown/visit/booking/investigation/task/process`. Новые шаблоны имеют
  стабильные `template_key`; запись связана с конкретным ID события через
  `booking_target_step_id`, независимо от вставок, одинаковых названий и перенумерации.
- В карточке записи — «На какую дату вы записались?». `appointment_date` — полученная
  дата, не срок действия «записаться» и не время уведомления. Время самого события
  задаётся в его карточке. Собственный прежний срок/таймер записи показан отдельно,
  не переносится и не стирается автоматически; нового времени оформления записи нет.
- `POST /route/steps/{id}/booking`: UUID `request_id`, `complete`, `appointment_date`,
  `target_step_id`, `expected_target_revision`, `confirm_target_change`,
  `target_reminder_action=keep|profile`. Сохранение даты/согласованного расписания цели,
  опциональное завершение текущей записи и receipt — одна транзакция.
  «Сохранить дату» не завершает; «Я записался» завершает запись, не будущий визит.
- При известной цели дата сохраняется в неё, не в промежуточную подготовку. Другая
  дата, точное время или индивидуальный таймер цели требуют явного подтверждения;
  ревизия другого окна даёт 409. `keep` не сдвигает абсолютный таймер, `profile`
  явно сбрасывает его. Выполненное событие не переписывается. Очистка полученной даты
  не стирает расписание цели: для этого надо открыть саму цель.
- Неизвестная дата/отсутствие связи допустимы с явным пояснением. Исключение/удаление
  цели обнуляет связь, не выбирает следующего врача. Pending можно редактировать,
  но нельзя завершать/уведомлять; подготовка перед событием задерживает его уведомления.
- Новые свои шаги имеют явный вид. В конструкторе доступны размещение перед исходной
  позицией шаблона, собственные ключи/цели и порядок своих шагов. В действующем маршруте
  добавление перед событием использует `?before_step_id=...` (не поле тела запроса).
- Старые шаги получают `unknown`, без классификации по словам/источнику, перестановки
  и очистки истории. Незавершённый шаг можно явно уточнить. Для выполненного `unknown`
  разрешено только уточнение вида запросом `{"kind":"visit"}` либо другим известным
  видом, без изменения даты/отметки/текста; к уточнённому визиту можно добавить назначения.
- UUID защищает повтор в открытой форме. После перезагрузки/выхода из карточки
  неопределённый запрос сначала проверяйте через маршрут; клиентское восстановление
  UUID между перезагрузками не реализовано. Серверный receipt долговечный.
- Бот явно завершает визит **без** ввода назначений и даёт ссылку на его карточку.
  Кнопка «Я записался» в чате не переносит дату и не завершает будущее событие.
  В `/status` и пушах полученная дата отдельно от срока задачи.

**Миграция:** SQLite при `init_db` идемпотентно добавляет поля смысла/связи/даты в
`route_steps` и `users.contains_demo_data` (default false). Существующие сроки, тексты,
порядок и receipts сохраняются. Новые шаблоны не пересобирают прежние маршруты массово.
Старый источник может оставаться непроверенным; медицинская/правовая экспертиза
не заменяется тестами. Для уже существующего PostgreSQL нужна отдельная миграция схемы;
PostgreSQL в этом пакете не проверен. Перед отдельно согласованным обновлением БД —
резервная копия и проверка миграции на копии, без второго polling.

## Выбор и смена поликлиники

- В обычном каталоге прикреплённая поликлиника отмечена; случайная замена другой
  кнопкой/меткой невозможна. «Профиль → Сменить» открывает `/orgs?mode=change`:
  только поликлиники региона профиля, старый и новый выбор, затем подтверждение.
  Это настройка МедМаршрута, не официальное прикрепление к организации.
- `POST /api/v1/me/clinic` принимает `attached_clinic_id`, обязательное
  `expected_clinic_id` (включая `null` для первого выбора), `expected_region`.
  Сохранение атомарное. Конфликт другого окна — 409 и новое подтверждение после
  обновления профиля, а не слепая перезапись. Повтор успешного выбора безопасен.
- Settings/consent не позволяют заменить или убрать существующую поликлинику.
  Смена региона со сбросом несовместимого выбора требует `confirm_clinic_reset`,
  `expected_clinic_id` и `expected_region`; интерфейс предварительно предупреждает.
- Зависимые незавершённые шаблонные шаги показывают выбранные название/адрес либо
  «Поликлиника не выбрана». Распознаваемые старые заглушки №12/каб. 304 исправлены
  проекцией без массового переписывания БД; ручные места и завершённые факты сохранены.

**Обновление схемы:** при запуске добавляются `route_steps.reminder_mode`,
`reminder_at`, `activated_at`, `reminder_revision`. Существующие сроки сохраняются,
старые строки получают режим `profile` без выдуманного таймера. Перед обновлением
сделайте резервную копию БД и не запускайте старый и новый bot одновременно.
Миграция проверена только на изолированных БД; боевой прогон требует согласования.

## Единый экран организаций и карты (M1–M4)

- `/orgs` содержит одну карту и список из одного набора результатов. Тип, регион
  и поиск меняют обе части; фильтры каталога не меняют профиль или прикрепление.
  Карточка и метка выделяют организацию и открывают адрес, часы, телефон и услуги
  на этом экране. Карта и список сохраняют естественный порядок; явный выбор
  переводит доступный фокус к выбранной карточке.
- Старые `/orgs/:id` открывают тот же экран, загружают организацию и выставляют
  её регион/тип. В режиме смены недоступные тип/регион объясняются, ограничения
  выбора не снимаются. Ошибка загрузки не выдаётся за пустой каталог.
- `GET /api/v1/orgs`: если `region` **не передан**, используется регион профиля
  (совместимость с онбордингом). Явные `region=` или `region=Все` снимают
  ограничение; конкретный регион фильтрует выдачу. Поиск по названию/адресу
  регистронезависим, включая кириллицу; `%` и `_` — буквальные символы.
- Карта обновляет метки/камеру без пересоздания SDK при выборе или фильтрации.
  Организации без валидных координат доступны в списке; их карта не выдумывает.
  Конфигурация карты и загрузка SDK/готовности ограничены тайм-аутами по 12 секунд
  (до 24 секунд суммарно); ошибка предлагает отдельный повтор загрузки карты.
  При отсутствии ключа/сети/SDK контакты и услуги остаются доступными.
- Две модельные организации из `content/SOURCES.md` помечены в подробностях,
  звонок по их демонстрационным телефонам отключён. Остальные контакты справочные.
- Локальные API/handler/SDK-mock проверки не заменяют приёмку реальной карты
  с доменным ключом в мобильном/веб-MAX. Секреты, рабочая БД и деплой не нужны
  для этих тестов; миграция схемы в этом пакете не требуется.

## Переменные окружения

Заполняются в `.env` (образец без секретов — `.env.example`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MAX_BOT_TOKEN` | токен бота MAX (обязателен для бота и проверки подписи initData) | — |
| `DATABASE_URL` | DSN базы; SQLite-файл в смонтированном `database/` | `sqlite:///./database/app.db` |
| `MINIAPP_PUBLIC_URL` | публичный https-адрес мини-апа (подсказки бота) | — |
| `MEDROUTE_DOMAIN` | домен для Caddy в prod-профиле | `localhost` |
| `DEV_BYPASS_AUTH` | только локально: вход без initData под демо-пользователем | `false` |
| `TEST_API_TOKEN` | токен тестового доступа к API для платформы (пусто = выключен) | — |
| `ALLOWED_ORIGINS` | CORS для dev-сервера Vite | `http://localhost:5173,...` |
| `YANDEX_MAPS_API_KEY` | публичный ключ JS API v3 Яндекс.Карт, ограниченный доменом | — |
| `TZ` | часовой пояс контейнеров (настраивается в compose) | `Europe/Moscow` |

**Порты:** приложение — `8000` (публикуется на `127.0.0.1:8000`); Caddy (prod) — `80/443`;
Vite (dev) — `5173`.

**Зависимости:** Python — `requirements.txt` (fastapi, uvicorn, sqlalchemy, pydantic,
pydantic-settings, maxapi, python-dotenv, reportlab, tzdata); мини-ап — `web/package.json`
(React 19, @maxhub/max-ui 0.5, vite). Автотесты из корня проекта:
`python -m pip install -r requirements-smoke.txt`, затем `python -m pytest`.
В Windows используйте Python из `.venv`: `.venv\Scripts\python.exe -m pytest`.

**Внешние сервисы и интеграции:**
- MAX Bot API (`platform-api2.max.ru`) — бот, initData, диплинки `startapp`;
  для работы бота нужен доступ в интернет. Это единственный внешний сервис,
  без которого невозможно воспроизвести проверку основного сценария
  (мини-приложение обязано запускаться внутри MAX).
- Яндекс.Карты — встроенная карта организаций через JS API v3; при отсутствии ключа
  остаются список организаций и внешние действия построения пути/поиска адреса.
  Ключ задаётся в `YANDEX_MAPS_API_KEY` и в кабинете Яндекса ограничивается доменом
  боевого мини-приложения.

## Работа с данными

- SQLite (`database/app.db`): пользователи, маршруты, шаги, дневники здоровья,
  курсы лекарств и отметки приёма, напоминания, журнал уведомлений.
- Справочники (регионы, организации, шаблоны маршрутов) — вне кода, в
  `content/*.json`; синхронизируются при каждом старте: добавить организацию =
  правка JSON без кода.
- 152-ФЗ: согласие — блокирующий экран онбординга; «Удалить мои данные» в
  профиле стирает аккаунт целиком (DELETE `/api/v1/me/data`); пароля нет —
  вход по подписанному initData из MAX.
- Показатели в интерфейсе и PDF — только факты; интерпретация («норма» и т.п.)
  отсутствует сознательно, оценка — работа врача.

## Тестовые данные и проверка

**Тестовый доступ к API** (для автоматической проверки платформой):
- `DATA-API.yaml` — перечень обязательных проверок (методы, параметры, роли,
  ожидаемые статус-коды и форматы ответа);
- `TEST-DATA.json` — тестовая учётная запись, тестовые данные, порядок проверки;
- доступ включается переменной `TEST_API_TOKEN` (сгенерировать:
  `python -c "import secrets; print(secrets.token_urlsafe(32))"`), запросы с
  заголовком `X-Test-Token` работают под тестовой учётной записью (id 909001);
- `openapi.json` — полное машинное описание API (OpenAPI 3.1), интерактивно — `/docs`.

**Демо-данные в боте** — для живого показа без ручного ввода:
- `/demo` — наполняет пустой аккаунт синтетической историей: 8 шагов (7 выполнены
  в прошлом, будущий контроль — текущий), состоявшийся приём и внесённые в рамках
  демо назначения. Дневники/отметки за 30 дней заканчиваются вчера; дата вычисляется
  при вызове в поясе профиля, не при импорте. Два отдельных Reminder явно независимы
  от очереди маршрута. Повтор полного готового набора — no-op; свои данные не заменяются;
- `/wipe` — очищает маршрут, дневники и лекарства (аккаунт и согласие остаются).

Новые аккаунты создаются **пустыми** — автосида нет. Все демо-данные
синтетические, флаг `contains_demo_data` помечает их в приложении и PDF даже после
добавления своих записей/удаления маршрута; очищается вместе с данными через `/wipe`.
Справочник содержит в том числе две вымышленные организации; контакты и источники
описаны в `content/SOURCES.md`. Статус экспертной проверки источников остаётся явным.

## Пошаговый сценарий проверки

1. В согласованном тестовом MAX-аккаунте найдите **@t24_hakaton_max_bot** → `/start`
   → «Открыть МедМаршрут». Не запускайте второй polling. `/demo` доступен после входа/согласия
   и только для пустого аккаунта; не заменяйте рабочие данные.
2. Онбординг: выбрать город из списка пилотных регионов → согласие.
   *Ожидаемо:* главный экран с пустым маршрутом (или демо-маршрутом после `/demo`).
3. «Маршрут» → «Свой маршрут» → «Записаться к терапевту».
   *Ожидаемо:* 3 шага без автодат: запись → подготовка → врачебный визит; один текущий,
   прикрепление необязательно. Для хронического контроля база состоит из 4 шагов.
4. В записи внести будущую дату, выбрать явную цель → «Сохранить дату»:
   запись ещё текущая, дата у нужного визита, не подготовки. «Я записался» завершает
   только запись. Будущий визит пока не напоминает. Завершить подготовку без окна назначений.
   На визите «Я это сделал» → «Отмена»: маршрут не изменён. Повторить → добавить два
   назначения с видами и необязательными датой/временем → подтвердить.
   *Ожидаемо:* визит выполнен, назначения вставлены сразу после него,
   первое — текущее, остальные незавершённые — ожидающие. Альтернатива — явное
   «Без назначений». Кнопкой «Отменить выполнение» можно вернуть выполненный шаг;
   таймлайн остаётся доступным и после завершения всего маршрута.
5. «Дневники» → давление → 124/82, пульс 71. *Ожидаемо:* график и история обновились.
6. «Лекарства» → добавить курс «Эналаприл 10 мг» 08:00/20:00 → отметить приём.
7. «Сводка для врача» → PDF с агрегатами за 30 дней; кнопка «в чат» — тот же PDF
   присылает бот (или команда `/svodka`).
8. Профиль → «Удалить мои данные». *Ожидаемо:* аккаунт удалён целиком; следующий
   вход начинается с онбординга.
9. Машинная проверка API — по `DATA-API.yaml` с заголовком `X-Test-Token`;
   проверка завершается `DELETE /me/data` (сброс учётной записи).

## Известные ограничения

- Нет интеграции с МИС/ЕГИСЗ: назначения вносятся пользователем вручную
  (архитектура допускает замену источника данных).
- Диспансеризация и другие сложные процессы — организационный каркас по реально
  сообщённому плану, не автоматически сформированная медицинская программа.
  Скрытый `family` не предоставляет общий доступ или общие уведомления.
- Телефоны и режимы организаций — справочные из открытых источников.
- Интеграции с гос-ИС нет; даты обычного маршрута вводит человек, демо помечено.
- Локальные HTTP/handler/клиентские проверки не заменяют медицинскую редактуру,
  браузерную приёмку, мобильный/веб-MAX и реальные таймеры/доставку.
- LLM не используется: сценарии и тексты детерминированные.
- Бот: один экземпляр на токен (long polling); напоминания приходят при
  запущенном контейнере `bot`.

## Остановка и повторный запуск

```bash
docker compose down            # остановить (данные в ./database сохраняются)
docker compose up -d --build   # запустить заново (справочники синхронизируются при старте)
```

Полный сброс данных: `docker compose down && rm -rf database/*` (удалит БД всех
пользователей).
