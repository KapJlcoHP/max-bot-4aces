# Контракт смысла шагов и записи на событие · S6–S9

18.10.2026. Реализация по продуктовой матрице `medroute-next/S8-EDITORIAL-DECISIONS-2026-10-18.md` (в соседнем каталоге рабочего пространства). Это организационный помощник, не медицинский протокол и не интеграция записи в МИС. Экспертная проверка медицинских/правовых источников этим контрактом не заменяется.

## 1. Данные и совместимость

- `kind`: `unknown | visit | booking | investigation | task | process`. По умолчанию `unknown` для старых записей и запросов без поля. `visit` означает именно врачебную консультацию, не запись, исследование, выдачу документа, экспертизу или поступление.
- `template_key`: nullable стабильный ключ шага внутри версии сценария; новые JSON-шаги содержат `key` и `kind`. Старым данным ключи/виды по названиям не присваиваются.
- `booking_target_step_id`: nullable ID конкретного незавершённого события **того же маршрута**. Цель имеет вид `visit`, `investigation`, `task` (административное событие) или `process`, не `booking/unknown`. Запись не может ссылаться на себя или цель до неё. Удаление цели явно обнуляет ссылки, не перепривязывает их к соседям.
- `appointment_date`: nullable дата полученного события, внесённая пользователем в шаг записи. Это **не** `deadline` действия «записаться». Старые `deadline/deadline_time` не копируются, не очищаются и не переименовываются.
- `reminder_revision`: существующая ревизия расписания возвращается в DTO для проверки изменения цели в другом окне. Изменение вида/связи тоже инвалидирует старый снимок увеличением ревизии.
- `users.contains_demo_data`: явная маркировка загрузки синтетического демо, default false. Сохраняется после своих дополнений/удаления маршрута, сбрасывается только при полной очистке содержимого; UI/PDF предупреждают о возможном смешанном происхождении.
- `source/source_id/reason` сохраняются. Удаляется только UI-блок объяснения происхождения; источник остаётся доступен.

SQLite: добавить nullable поля и `kind NOT NULL DEFAULT 'unknown'` идемпотентной миграцией. Не менять тексты/порядок/сроки/историю/таймеры прежних шагов. Сохранять таблицу receipt. Новая схема поддерживает PostgreSQL через модели; обновление уже существующей PostgreSQL-схемы требует отдельной явно выполненной миграции, не обещается автоматически.

## 2. Создание, частичный PATCH, размещение

- `StepAddIn`, `CustomStepIn`, `DoctorAssignmentIn` принимают `kind` с безопасным default `unknown`. Ручной UI явно выбирает вид, обычно `task`; чипы исследований имеют `investigation`, «Приём специалиста» — `visit`, процедуры явно одно выполнение/конечный этап. `DoctorAssignmentIn` для свободного ввода записи поддерживает `appointment_date` отдельно от `deadline`; цель назначается позднее явно в карточке, дата не создаёт таймер до согласованного применения к цели.
- `StepUpdateIn` принимает `kind` и `booking_target_step_id` с различением пропуска/null. `kind=null` недопустим. Для completed изменение расписания/связей и уже известного вида запрещено. Единственное исключение — явное уточнение `unknown` запросом только `{"kind":"visit"}` (либо другим известным видом), без перезаписи даты/отметки/текста истории. Это даёт возможность внести назначения к прежнему выполненному визиту, не заставляя отменять историческое выполнение. Никакой эвристики по словам/источнику.
- Запись не принимает новое точное `deadline_time` (время оформления не спрашивается). Уже сохранённый старый срок/время остаётся видимым в отдельном блоке «Прежний срок действия записи» с возможностью явного изменения/очистки. Изменение вида старого шага не стирает его расписание.
- POST добавления шага поддерживает `before_step_id` наряду с прежним `after_step_id` (оба одновременно запрещены). Вставка перед незавершённым событием доступна явно; исторические done-шаги не переставляются. Порядок пересчитывается, current всегда первый незавершённый.
- `CustomStepIn` дополнительно принимает `client_key` (необязательный уникальный временный ключ), `booking_target_key` (ключ шаблона либо client_key другого своего шага), `before_position` (необязательная исходная позиция шаблона, перед которой вставить свой шаг). При исключённой/неизвестной позиции — явная ошибка, не перенос в конец вслепую. Для маршрута с нуля порядок — порядок массива, который UI позволяет изменить.
- Шаблоны используют `booking_target_key` для явной связи. После создания шагов ключи разрешаются в ID, исключённая цель оставляет запись без связи. API предпросмотра возвращает `key`, `kind`, `booking_target_key`, `description` вместе с прежними полями.
- Передача `appointment_date` при создании своей записи сохраняет сведения в ней, но не затирает расписание цели. Применение к цели — только явная операция ниже. `StepAddIn` может получить `booking_target_step_id`; цель проверяется сервером.

## 3. Атомарная операция записи

`POST /api/v1/route/steps/{id}/booking`:

```json
{
  "request_id": "UUID",
  "complete": false,
  "appointment_date": "2026-10-24",
  "target_step_id": 123,
  "expected_target_revision": 0,
  "confirm_target_change": false,
  "target_reminder_action": "keep"
}
```

- Ответ — `CompleteStepOut` (`step`, полный `route`, `next_step`), сохраняемый в долговечном receipt. Операции booking/assignments имеют независимый отпечаток содержимого, но общий пользовательский namespace UUID: ключ нельзя переиспользовать для другого действия.
- Допустимы `appointment_date=null`, `target_step_id=null`: неизвестная дата и отсутствие однозначной связи не блокируют фиксацию записи. UI явно сообщает о непривязанной дате и отсутствии напоминаний о событии из этой записи.
- `complete=false`: сохранить сведения и согласованную дату цели без завершения исходного шага. `complete=true`: то же плюс завершение **только текущей записи**. Pending допускает редактирование, не завершение; done не переписывается. Обычный `/complete` сохраняет явное завершение без внесения/переноса даты, включая кнопку бота.
- Если есть цель и непустая дата, изменить только дату цели; её точное время сохраняется. `expected_target_revision` обязателен для изменения цели, несовпадение — 409. Если у цели другой срок, точное время или индивидуальный режим, требуется `confirm_target_change=true`; UI показывает старое и новое значение. Завершённую цель не менять.
- `target_reminder_action`: `keep | profile`. При `keep` собственный абсолютный таймер остаётся на месте только после явной проверки/подтверждения; просроченный новый таймер не сохранять. `profile` явно сбрасывает переопределение. Режим `hour` требует точного времени цели. Пересчёт дедупа только при реальном изменении расписания/режима.
- Пустая `appointment_date` очищает сведения о полученной дате в записи, **не стирает дату/таймер цели**. UI объясняет: срок события меняется/очищается отдельно в его карточке. Так старые даты не удаляются молча.
- Проверки, завершение, изменение даты/дедупа и receipt — одна транзакция под существующей блокировкой маршрута. Повтор того же UUID возвращает сохранённый снимок; другое содержимое — 409. При неопределённом сетевом исходе UI замораживает исходное тело для безопасного повтора в открытой форме.
- Не регрессировать старые receipts S4: запросы назначений без новых полей должны сохранять прежнюю канонизацию отпечатка.

## 4. Интерфейс и каналы

- Текущий `visit`: форма S6 до мутации, отмена ничего не меняет; явное завершение без назначений. Done-визит: отдельное добавление пакета. Остальные виды — штатное завершение без формы. Сервер не принимает новый пакет назначений от заведомо неврачебного вида; исторический receipt по UUID читается до проверки состояния/вида.
- Booking: поле «На какую дату вы записались?», выбор конкретной цели, результат «Событие назначено на …» (для врача «Приём назначен на …»). Без времени оформления записи. «Сохранить дату» не завершает, «Я записался» завершает текущую запись. При нескольких возможных целях пользователь выбирает, не применяется первый/следующий врач автоматически.
- Срок действия записи и его напоминание отдельно от полученной даты; старый таймер не прячется. Время события пользователь меняет в карточке целевого визита/исследования. Правила N1–N3 и единственный current не меняются.
- `/status`, пуши, Home/таймлайн/PDF отличают срок шага от сведений о полученной записи. Чат завершает визит явно без назначения и даёт ссылку на выполненный визит для внесения назначений; не притворяется формой Mini App.
- Обычные новые шаблоны без автодат. Демо — отдельная согласованная синтетическая история: посещения в прошлом, будущий контроль не completed, независимые Reminder явно названы отдельными.

## 5. Приёмка

Изолированные тесты: миграция/повтор и неизменность истории; виды/явные ссылки readback; исключение/удаление цели и одинаковые названия; вставка перед событием; роль ручных/чипов; S4 rollback/UUID/единственный current; booking save/complete/unknown/null/конфликт/таймер/повтор/rollback; клиентские обработчики отмены/двойного клика/ошибки/неопределённого ответа; бот и несколько поясов демо. Затем tsc, клиентский тестовый набор и production build. Медицинская экспертиза и живой MAX/карта/доставка остаются отдельной приёмкой.
